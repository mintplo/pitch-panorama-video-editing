# 파노라마 스티칭과 추적 뷰 편집

## 입력에 따라 시작 단계 선택

파일이나 폴더를 받으면 아래 1절의 목록 작성과 무결성 검사를 먼저 한다. 각 파일의 초·중·후반 프레임을 보고 한 장면으로 이어진 전체 시야가 있는지 확인한다. 가로세로 비율이나 파일 개수만으로 이미 스티칭됐다고 판단하면 단일 카메라 영상, 좌우 화면을 나란히 담은 영상, 이미 확대된 추적 뷰를 혼동할 수 있다.

- **기존 파노라마에서 추적 뷰 만들기.** 좌우 짝 찾기, 카메라 간 동기화, 투영·합성을 건너뛴다. 원본 파노라마의 첫 표시 프레임을 0초로 삼아 전체 프레임에서 피사체를 관측하고, 촬영된 유효 영역 안에서 크롭 경로를 만든다. 축구는 [공 추적 절차](FOOTBALL_WORKFLOW.md)를 적용한다. 가장자리·롱패스 등 대표 클립을 확인한 뒤 파노라마에서 직접 렌더하고 5절의 검수를 수행한다. 트림은 이 파일 기준으로 영상과 원음에 한 번만 적용하며 첫 음성·영상 PTS 차이를 보존한다.
- **좌우 원본에서 시작하기.** 1절의 짝 확인부터 4절의 스티칭까지 진행한 뒤 요청한 구도로 편집한다. 두 종류가 섞여 있으면 촬영 구간별로 판단한다. 추적 뷰 요청에서 같은 구간의 유효한 파노라마와 카메라 원본이 함께 발견되면 기존 파노라마를 우선 사용하고, 그 구간을 중복 렌더하지 않는다. 입력 종류나 대상 구간을 판별할 수 없고 그 선택이 결과를 바꾸면 해당 파일에 대해서만 확인을 요청한다.

작업 양식의 `source_pairing.inventory`에 입력 종류와 판단 근거를 남긴다. 기존 파노라마를 사용한 출력 구간은 `panorama_source`에 그 파일을 기록한다(일반 촬영은 `output.segments`의 해당 항목, 축구는 해당 쿼터). 카메라 간 동기화·투영 설정은 비워 두고 해당 검수 항목은 `not_applicable`로 표시한다. 기존 영상에 포함된 접합 오류나 잘림이 추적을 제한하면 결과 타임코드에 남긴다.

## 1. 원본 검사와 좌우 짝 확인

원본 위치는 한 곳 또는 여러 곳을 받을 수 있다. 지정된 각 폴더 안의 하위 폴더까지 살펴보고 영상 목록을 합친다. 한 폴더에 좌우 영상이 섞인 경우와 카메라마다 다른 폴더에 저장된 경우 모두 이 목록에서 짝을 찾는다. 폴더 이름은 카메라 방향을 추정하는 단서로만 쓴다. 파일을 이름순으로 나란히 맞추면 한쪽 녹화가 빠졌을 때 이후 짝까지 밀릴 수 있다.

1. **원본 경로와 검사 결과를 기록한다.** 작업 양식에서 입력 폴더가 하나면 `source_directory`, 여럿이면 `source_directories`에 각 경로를 적는다. `source_pairing.inventory`에서 각 영상은 입력 폴더와 그 안의 상대 경로로 식별한다. 두 카메라가 모두 `0001.mp4`를 만들어도 별도 파일로 다루고, 입력 폴더가 서로 겹쳐 같은 파일을 두 번 발견하면 한 번만 센다. 폴더가 비었거나 읽을 수 없으면 그 사실을 알린다.
2. **각 파일이 실제로 읽히는지 검사한다.** ffprobe로 영상·음성 스트림, 해상도, 회전, 시작 PTS, 타임베이스, 재생 길이를 읽고 초·중·후반을 짧게 디코딩한다. 헤더에 표시된 길이와 실제 읽히는 끝이 다르면 손상이 의심되는 구간을 연속 디코딩해 마지막으로 읽힌 시각을 적는다. 열리지 않는 파일, 중복 사본, 사용자가 제외한 파일도 사유와 함께 목록에 남긴다.
3. **후보를 좁히고 장면으로 짝을 확인한다.** 파일명·촬영 시각·길이로 후보를 고른다. 카메라 시계 차이나 분할 녹화가 있을 수 있으므로 중첩 시야에서 같은 사람이 선을 통과하거나 공을 차는 등 식별 가능한 사건을 찾는다. 가능하면 서로 떨어진 두 시점 이상에서 양쪽 원본 시각을 적고 사건의 순서를 대조한다. 뚜렷한 소리는 대응 시각을 찾는 단서로 쓴다. 정지 배경이 같거나 관중 소리가 비슷한 것만으로는 짝을 확정하기 어렵다. 공통 시야의 양끝에서 각 카메라에만 보이는 배경으로 카메라의 좌우 방향을 확인하고 같은 카메라의 중복 사본을 걸러낸다.
4. **파일별로 맞는 구간을 기록한다.** `source_pairing.assessments`에는 왼쪽·오른쪽 파일(없는 쪽은 `null`), 아래 판정, 근거가 된 양쪽 원본 시각, 함께 쓸 수 있는 구간과 그 기준 카메라, 손상·공백·후속 조치를 적는다. 공통 구간은 2절의 시간 변환과 실제 디코딩 범위로 정한다. 예를 들어 왼쪽은 20분짜리 한 파일이고 오른쪽은 두 파일이면, 오른쪽 각 파일이 왼쪽의 어느 구간과 겹치는지 따로 확인한다. 분할 경계에서 빠지거나 중복된 시간을 기록하고 같은 시간을 두 번 사용하지 않는다. 축구 쿼터 번호는 짝을 찾은 뒤 실제 경기 순서와 사용자 지시에 따라 배정한다.

| 판정 | 판단 근거와 처리 |
|---|---|
| 확인됨 (`confirmed`) | 같은 사건과 좌우 시야가 확인됐다. 사용 가능한 구간을 적고, 손상이나 공백으로 요청 분량이 빠지면 그 범위를 별도로 알린다. |
| 판단 보류 (`ambiguous`) | 여러 후보가 남거나 식별할 사건이 부족하다. 비교한 파일과 판별에 필요한 단서를 적는다. |
| 불일치 (`mismatch`) | 시계 차이를 고려해 대조해도 사건 순서가 양립할 수 없거나 두 파일이 같은 카메라 영상임을 확인했다. 그 조합을 제외하고 남은 후보를 확인한다. |
| 짝 없음 (`unmatched`) | 받은 파일을 모두 대조해도 상대 파일을 찾을 수 없다. 어느 파일의 상대편이 필요한지 알린다. |

**사용자에게 알리는 시점.** 스티칭 전에 확인된 짝과 공통 구간을 간단히 보고한다. 요청한 편집에 영향을 주는 누락·불일치·판단 보류·손상은 발견하는 대로 파일명, 확인한 장면 또는 오류 시각, 영향을 받는 분량과 함께 알린다. 결정이 필요한 구간만 보류한다. 이미 제외를 지시받은 짝은 `excluded_sources`에 기록하고, 새 원본이 들어오면 관련 판정과 공통 구간을 갱신한다.

예를 들어 오른쪽 원본의 뒷부분이 손상됐다면 다음처럼 알린다.

> `left-B.mp4`와 `right-B.mp4`는 같은 킥과 재개 장면이 보여 짝이 맞습니다. 오른쪽 영상이 원본 12분 40초에서 끊겨 마지막 2분은 스티칭할 수 없습니다. 오른쪽 원본 전체가 있으면 보내 주세요. 없다면 앞 12분 40초만 쓸지, 이 짝을 통째로 제외할지 알려 주세요. 확인된 다른 짝은 계속 편집하겠습니다.

전체 파노라마 보존과 피사체를 따라가는 크롭 중 요청한 출력을 정한다. 여백을 허용한 파노라마에서는 시야 보존이, 검은 테두리를 없앤 크롭에서는 매 프레임 유효한 촬영 영역이 기준이다. 일반 촬영에 축구 쿼터 분할이나 경기 시작 트림을 자동 적용하지 않는다.

## 2. 같은 순간을 찾는 법

오른쪽을 기준으로 잡은 경우, 각 원본의 **첫 재생 프레임을 0초**로 둔다. 원본 PTS가 0에서 시작하지 않으면 스트림 시작값을 반영해 이 시간계로 변환한다. 초·중·후반에서 두 카메라가 공유하는 짧고 식별 가능한 사건을 찾는다. 오디오 파형 상관으로 후보를 구하고, 중첩 영역의 발 접촉·선 통과 같은 시각 사건으로 확인한다.

- 대응점마다 왼쪽 시각 `tL`과 오른쪽 시각 `tR`을 기록하고 `tL = (1 + drift) × tR + offset`을 맞춘다. 예를 들어 같은 사건이 오른쪽 10초, 왼쪽 8초이고 차이가 계속 일정하면 offset은 **−2초**다. 초반은 맞고 후반만 어긋나면 여러 대응점으로 drift를 다시 추정한다. 녹화 공백처럼 오차가 갑자기 바뀌면 구간을 나눈다.
- 오른쪽 시각과 변환된 왼쪽 시각이 **둘 다 실제로 존재하는 구간**만 사용한다. 그 시작을 오른쪽 기준 `common_start`로 기록한다. 파노라마에서 앞부분을 `trim`초 자른 뒤 출력 `u`초는 오른쪽 원본의 `common_start + trim + u`초다. 이 값으로 왼쪽 시각도 계산한다.
- 가변 프레임레이트 영상은 각 목표 시각에 가장 가까운 실제 프레임 PTS를 사용한다. FPS로 프레임 번호를 환산하거나 양쪽 디코더에서 한 장씩 순서대로 꺼내면 시간이 갈수록 장면이 어긋날 수 있다.

구간, 대응점, 잔여 오차, 기준 카메라와 오디오 소스를 로컬에 기록한다. 촬영 양식의 `sync_config`가 그 기록을 가리키게 한다. 축구 양식에서는 쿼터별 `sync_offset_seconds`, `sync_drift`, `trim_timebase`를 채운다.

## 3. 카메라 보정과 접합부 진단

회전과 렌즈 왜곡을 먼저 확인한다. 두 영상을 같은 방향으로 바로 세운 후, 여러 높이와 거리에 분포한 **고정 배경**의 공통점을 찾는다. 해당 렌즈와 해상도에 맞는 내부 행렬 K가 있으면 사용하고, 없으면 보정 촬영 또는 중첩 특징점으로 추정한다. 잘못 대응한 점을 제거하고 상대 회전을 추정해 원통 투영을 시험한다. 축소·크롭한 프레임으로 추정한 K는 최종 프레임의 크기와 원점에 맞게 변환한다. 공이나 선수가 접합부를 지나는 장면은 검수에 유용하다.

같은 시각의 두 프레임과 K·R을 이용해 [프레임 스티칭 도구](tools/stitch_frames.py)로 미리보기를 만든다. R의 방향은 **카메라 좌표계에서 공통 좌표계로**다. 여러 시점과 장면 깊이에서 확인하고, 적용한 보정을 `projection_config` 또는 쿼터의 `render_config`에 연결한다.

| 출력에서 보이는 현상 | 다음 확인과 보정 |
|---|---|
| 정지한 선·건물도 두 갈래로 보인다 | 같은 시점의 정지 배경으로 회전 방향, 왜곡, K의 해상도, 공통점 분포를 확인한다. 보정에 쓰지 않은 지점에서도 정렬을 확인한다. |
| 배경은 이어지는데 움직이는 대상이 둘로 보인다 | 먼저 양쪽 원본의 동일 동작을 프레임 단위로 비교한다. 시간이 맞으면 가까운 물체의 시차를 의심하고 접합선 위치를 조정한다. |
| 경기 중 특정 시점 이후부터 배경까지 틀어진다 | 장착 위치가 흔들린 시점을 찾는다. 해당 구간의 보정과 유효 영역을 다시 계산한다. |
| 중첩 폭이 너무 좁아 일관된 대응점을 찾기 어렵다 | 다른 시각의 프레임과 원본 방향을 확인한다. 계속 불가능하면 어떤 촬영 범위를 복원할 수 있는지 기록하고, 요청한 구도를 바꿔야 할 때만 사용자에게 선택을 구한다. |

## 4. 작업별 렌더 작성

공개 도구는 시간 정렬된 8비트 BGR **프레임 쌍**과 보정값을 받는다. 새 촬영의 영상 디코딩, 시간 대응, 크롭, 인코딩, 음성 결합은 로컬 스크립트에서 연결한다. 두 카메라가 고정되어 있는 구간의 처리 순서는 다음과 같다.

1. 실제 입력 크기와 K·R로 `build_maps(left_size, right_size, calibration)`를 호출한다. 크기는 각각 (가로, 세로)이며, 회전·크기·보정이 바뀌면 맵을 다시 만든다.
2. 출력 프레임 `i`의 시각 `u = i / 출력 FPS`에서 양쪽 원본의 목표 시각을 계산한다. 해당 프레임을 디코딩해 `blend_frames(left, right, maps)`로 합성한다.
3. 파노라마 전체 또는 그 프레임의 계획된 크롭을 출력한다. 검은 모서리를 허용하지 않는 작업은 `maps.covered`로 크롭 내부의 유효 픽셀을 검사한다. 검은 옷·그림자처럼 원본에서 실제로 어두운 픽셀도 있으므로 밝기만으로 여백을 판정하지 않는다.
4. 대표 클립에서 원본 음성과 화면을 먼저 함께 재생한다. 오른쪽 영상과 음성의 재생 원점이 같으면 음원도 `common_start + trim`에서 시작한다. 첫 비디오 PTS와 첫 오디오 PTS가 다르면 둘의 원점 차이까지 반영한다. 왼쪽 음원을 쓰면 시간 변환을 적용하고, 드리프트가 유의하면 오디오 길이도 출력 시간축에 맞춘다. 검증된 설정으로 원본에서 최종 렌더한다.

## 5. 검수와 인계

출력마다 예상 프레임 수, 첫 장면, 끝 장면, 길이·해상도·FPS·오디오 트랙을 실제 파일과 비교한다. 비디오와 오디오가 있는 MP4는 다음처럼 끝까지 디코딩한다. `OUTPUT`은 납품 파일의 경로로 바꾼다.

```sh
ffmpeg -nostdin -v error -xerror -i "$OUTPUT" -map 0:v:0 -map 0:a:0 -f null -
```

음성 없는 원본이면 영상 스트림만 검사하고 그 사실을 기록한다. 웹 재생용 MP4는 faststart로 내보내고 헤더의 `moov`가 `mdat`보다 앞에 있는지 확인한다. 동일한 속도의 원본 음성과 비교할 때는 [오디오 검사 도구](tools/verify_audio.py)의 `--source-start`에 **출력 0초에 해당하는 음원 재생 시각**을 전달한다. 리타이밍한 음성은 같은 시간 변환을 적용한 기준 음원 또는 각 구간의 시청각 사건으로 검사한다. 무음이나 반복음 때문에 판별이 어려우면 뚜렷한 사건이 있는 구간에서 다시 확인한다.

작업 기록에는 각 결과 파일, 사용한 원본·구간·설정·스크립트, 전체 검사 결과와 직접 재생한 장면을 남긴다. 예를 들어 “전체 디코딩 통과, 접합부는 초·중·후반 세 구간 재생, 가까운 피사체의 잔상은 출력 몇 초에 남음”처럼 확인한 범위를 쓴다. 결과를 수정하면 영향을 받은 검수를 최종 파일에 다시 적용한다.
